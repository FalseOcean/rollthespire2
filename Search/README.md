# Current Search source map

`Semantics/SearchCompiler` compiles player Query/commitments, and `Compilation/ExactSearchExecutionRequestFactory` is the single execution admission boundary. `LegacySearchQueryAdapter` reads retained legacy numeric filters into that same Query path; `CompiledSearchEvaluationProjector` produces final validation criteria. Numerical authority compilation receives the existing `SearchContext` directly.

`FamilyExecution` contains **Filter implementations** for N/S/R/C/W/A/E/T/M and their applicable CPU/GPU realizations, bounded allocations, private ordinals and Family-owned pricing/survival. This list does not imply that every Family has every physical implementation. Under `Planning`, `FamilyExecutionCoordinator` registers applicable Families; `FamilyPlanner` greedily orders their available units from Survival and Cost projections. The coordinator is not a second game predictor.

`Runtime/ProductionSearchSession` owns the whole Search lifecycle: ranges, batches, cancellation, target count, Filter execution, Exact handoff, ordered cursor commit and results. Public ABI1 remains ordered batch-local ordinals.

`Runtime/ProductionExactSearchEvaluator` calls `RuntimeProfileRegistry.Predict[FromRootHash]` and the required canonical domain predictors. `Runtime/ProductionQueryValidator` checks the returned prediction against Query. `SearchQueryEvaluation` carries disposition/evidence/Witness; it does not predict game rules.

Predictor request/result/profile contracts live in `Core/Prediction`; game algorithms remain in their existing `Core/Neow`, `Effects`, `World`, `Rewards`, `Relics`, `Events` and `Merchant` domains. `Core/Authority/RuntimeContextAuthoritySnapshot` is shared immutable context; capture belongs to Infrastructure. ## Maintaining game updates, RNG and model rules

Use this bounded route when a game update or a concrete counterexample changes prediction rules. Version policy belongs to PRODUCT_STRATEGY (internal record omitted); responsibilities and current evidence belong to PROJECT_ARCHITECTURE (internal record omitted) and CURRENT_STATUS (internal record omitted).

1. **Establish the actual baseline.** Record checkout/HEAD and existing edits, the resolved build reference and loaded `sts2` assembly identities, and release metadata provenance. Follow [BUILDING](../BUILDING.md) for `Sts2ReferenceDir`; retain binary path/hash and available assembly identity alongside source/decompilation provenance. A `GameSource` directory name alone does not identify the assembly. [GameVersionDetector](../Compatibility/GameVersionDetector.cs) prefers supplied runtime release information, then records its file fallback; an exact release version is not itself a binary hash or compatibility audit.

2. **Keep four identities separate.** Inspect [RuntimeVersionCompatibility](../Compatibility/RuntimeVersionCompatibility.cs) and [RuntimeProfileRegistry](../Compatibility/RuntimeProfileRegistry.cs): exact game identity, selected adapter `ProfileId`, RNG/generation `SemanticProfileId`, and compatibility confidence/blocked domains are separate fields. [RuntimeProfilePolicies](../Compatibility/RuntimeProfilePolicies.cs) owns shared rule selection; [RequestSupportScope](../Core/Authority/RequestSupportScope.cs) separately records the declared real-game promise baseline. Registration or a model Match does not establish official support. Resolve the actual version through current code; do not invent a mapping or replace provisional reuse with an “all unknown versions reject” policy.

3. **Compare the affected mechanism.** Start with the corresponding source from the identified game binary, then trace canonical seed → root hash → named/event stream → draws. [ProfileSeedRules](../Compatibility/ProfileSeedRules.cs), the selected profile, [Core/Seed](../Core/Seed), and [Core/Rng](../Core/Rng) are the RT2 entry points. Check slot ownership, stream names, draw bounds/rounding, shuffle draw count and order, pool eligibility/cleaning/sorting, side effects and continuation cursors. A correct PRNG primitive cannot compensate for a changed pool or one extra draw; limit the investigation to actual dependents.

4. **Trace every affected consumer.** Representative entrances are [Beta111PredictionProfile](../Core/Prediction/Profiles/Beta111PredictionProfile.cs) for demand-scoped observations and [NeowSingleplayerReplay](FamilyExecution/NeowSingleplayerReplay.cs) for independent N filtering. The latter has named-stream constants, local route copies and a separate [Fast RNG](FamilyExecution/Beta110FastRng.cs); its CPU/GPU and solo/party counterparts must agree where the changed rule applies. Follow actual obtain effects and reward/route continuation into their owners, rather than forcing all consumers through a complete information document or treating an observation continuation as a full checkpoint.

5. **Preserve the contracts while repairing rules.** Prediction works on captured/detached values; do not advance real `RunState`/RNG, and keep Godot/capture/UI work on the main thread. Public ABI1 remains ordered batch-local `LogicalOrdinal[]`. [ProductionExactSearchEvaluator](Runtime/ProductionExactSearchEvaluator.cs) retains final Query evaluation and the required common witness; Fast success alone cannot confirm a result. Keep missing observations local, preserve authored intent and unverified provenance, and retain real execution faults as faults. See the request/failure handbook (internal record omitted).

6. **Select existing checks for the changed meaning.** Inspect [functional Program.cs](../tests/functional/Rt2FunctionalChecks/Program.cs) before running; its early-return dispatch normally selects one relevant flag per invocation. Use `dotnet run --project tests/functional/Rt2FunctionalChecks -c Release -- <flag>` from the repository root. The pure RNG runner is separate; no `--seed-rng` functional flag is implied.

   | Change | Existing check entry |
   | --- | --- |
   | Seed/hash/state/draw vectors and version-resolution fixtures | `dotnet run --project tests/seed-vectors -c Release`; [vector authority](../Core/Verification/SeedRngVectorVerifier.cs) |
   | Runtime detection, profile availability and request support scope | `--runtime-version-profile` |
   | Bounded observations and final disposition/fault boundaries | `--predictor-closure`, `--exact-boundary` |
   | Opening acquisition order, obtain effects or common N/T/R/C witness | `--silken-tress-order`, `--capsule-obtain-policy`, `--wwp-commitment`, `--transformation-relic`, `--combination-regressions`, as affected |
   | Family numerical/physical implementation | The affected `--family-neow`, `--family-combat`, `--family-world` or `--family-ae` path, plus relevant existing GPU/native parity when GPU rules change |
   | Stateful continuation, capture or partial knowledge | The affected `--predictor-runtime-*` flag or `--predictor-partial-knowledge` |

7. **Record what the evidence proves.** After code changes, run the required Release build and relevant checks under AGENTS (internal record omitted), review the diff, and follow the assigned delivery boundary. For validation without deployment use `dotnet build -c Release -p:Rt2ModsDir=`. Retain seed/Query, declared context/operations, binary/profile identity, expected versus observed outputs and stream/cursor facts in existing diagnostics/evidence. Golden vectors establish their sampled primitives; managed/native parity, installed binary identity and actual gameplay acceptance are separate facts. Update the affected canonical facts and decision rationale when they change; a version bump or passing old vectors alone does not establish new game compatibility.
