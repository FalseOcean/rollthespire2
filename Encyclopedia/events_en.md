# Events: What Appears and What Happens Are Different Questions

> Applies to: **Slay the Spire 2 Beta 0.111.0**

## What You Want

Event filtering addresses two questions:

> **Which events may appear next in this Act?**
> **If a particular event occurs, what random result does it produce?**

You might want an event among the first few candidates, or additionally require a specified outcome upon encountering it. Both concern events, but their random mechanisms differ.

# Events Begin with a Random Queue

Each Act establishes its own event order from the seed: **a pre-shuffled event queue**.

Much of that order is determined before you reach a question-mark room. RT2 can therefore check an event's position among early candidates or the relative order of specified events.

# RT2 Filters the Raw Queue

Some entries in the game's original order can already be ruled out using known state.

RT2 excludes candidates that **facts established at the opening** prove unavailable, producing an order closer to possible gameplay.

The “event queue” here is more precisely:

> **The original order filtered using RT2's known conditions.**

It is a search view, not a second cleaned queue generated by the game itself.

# An Early Queue Position Does Not Guarantee an Encounter

Even after that filtering, the queue alone cannot prove the player will encounter an event.

Some eligibility rules depend on state upon arrival. The route also determines how many Event rooms the player visits.

The queue answers **which candidates the seed provides as the game looks for a suitable event**, not which events are guaranteed to happen in sequence.

# Results Use Another Layer of Randomness

Knowing an event's identity does not reveal everything that happens inside it. Many events have their own random process.

> **The queue** determines candidate order.
> **The event's own randomness** determines its concrete results.

Neither layer should automatically imply the other.

# Some Results Are Stable; Others Need More Premises

For some events, identity already supplies almost all required information and the result follows directly from the seed.

Others depend on player choices, the current deck, earlier event order, or extra consumption of a relevant RNG. Transformation events are examples that need clearer premises rather than being inherently unpredictable.

# How Does RT2 Handle This?

For order, RT2 restores the raw queue, applies static filtering from known facts, then checks the early candidates.

For results, RT2 assumes the event has occurred and checks its outcome using that event's rules.

> **Matching an event result does not prove that the event will appear.**

If both matter, require both its presence among the candidates and its specified result.

**What you may encounter** and **what happens once you encounter it** remain separate questions. RT2 answers them with established seed information without treating the candidate queue as a proven, reachable run route.
