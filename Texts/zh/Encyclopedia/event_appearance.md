# 事件出现性：队列不等于实际遇见

预测一个种子每幕的事件队列，是相对经济、也很有用的信息。可一旦问“第一个问号能否遇到指定事件”，需要计算和判断的事情就不同了。问号先要成为事件房，游戏还会从队列中跳过当时不符合条件或已经访问过的事件。因此，队列第 N 项并不是第 N 个问号实际遇到的事件。

这里也有路线的影响。有些路线没有问号，有些路线只有少量问号；队列中存在一个事件，并不意味着你怎样走都能遇到它。对于受先前经历影响的事件，还要知道到达时的金币、生命、牌组等资格，以及已经访问过哪些事件。把这些都纳入高速筛种，是另一份计算负担。

因此，对于具体事件的身份，我选择让筛种器提供队列信息。它会按当前配置还原候选顺序，计入对应开局的事件位置，并排除已知的静态不合法条目；依赖未来状态的资格仍需你判断。我认为这些信息已经足够帮助玩家寻找机会，但实际能否遇见，还要结合地图和游玩过程来看。每幕分别有自己的队列，跨幕共享候选池也不表示各幕共用同一条队列。

## 先筛问号的房间类型

有时你并不需要直接保证某个事件，只是希望前几个问号别变成战斗或宝箱。为此，事件页可以要求**第一幕第1个问号、前2个问号或前3个问号均为事件房**。

这项条件用于普通非教程单人，按进入问号的顺序计算，忽略相邻商店带来的房间限制。{{relic:JUZU_BRACELET}}只按本次查询开局中已确定的取得情况计入，不推演途中获得或失去它。

它回答的是“问号先成为哪类房间”。地图上是否有足够问号、到时能否遇到你要的具体事件，仍需结合路线和事件资格判断。

事件筛选见 [[events|事件]]，局外地图信息见 [[map|地图]]；对局中沿当前幕路线查看信息，可读 [[path-prediction|绘线预测]]。
